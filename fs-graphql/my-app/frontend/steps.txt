Step 1: Frontend dev.Dockerfile
1. First, understand the picture
Imagine that your React frontend is a small workshop. It needs Node.js, npm, your source code, and the packages your project depends on.
Docker builds a container environment with the tools required to run that workshop.

Your frontend source code
React components, package.json, Vite configuration

Frontend dev.Dockerfile
Instructions for preparing the environment

Docker image
A prepared environment with Node.js, dependencies, and app files

Running frontend container
Runs the development server so you can work on the app

The important distinction:
- Dockerfile: instructions for building the environment.
- Image: the prepared template produced by those instructions.
- Container: a running instance of that image.


Line 1 — FROM node:24
FROM node:24


Meaning: Start with an existing image that already contains Node.js 24.
Think of it like renting an equipped workshop instead of constructing every tool yourself.
Node.js base image

- Linux environment
- Node.js runtime
- npm package manager

Without this, you would need to choose and install a suitable runtime yourself.

Line 2 — WORKDIR /usr/src/app
WORKDIR /usr/src/app


Meaning: Set the working directory inside the container.
Imagine walking into your workshop and deciding that /usr/src/app is where all the work will happen.
Container filesystem
└── usr/
    └── src/
        └── app/     ← our working directory


Commands such as RUN npm install will run from this directory unless another directory is specified.
Docker creates the directory if it doesn't already exist.

Lines 3–4 — Copy package files and install dependencies
COPY package*.json ./

RUN npm install


This is an important part of understanding Docker builds.
First, COPY package*.json ./ copies matching package files, such as package.json and package-lock.json, from the build context into the working directory.
Then, RUN npm install installs the dependencies declared by the project.
Picture it like this:
Your project
package.json + package-lock.json

COPY package*.json ./

RUN npm install

Installed packages in node_modules


Why copy package files first?
Docker can reuse cached build layers when these files haven't changed. If you edit a React component but leave the package files unchanged, Docker may reuse the dependency-installation layer instead of installing everything again.
For reproducible installs, npm ci is often preferable when a valid package-lock.json exists. We can choose that based on your actual project.

Line 5 — COPY . .
COPY . .


Meaning: Copy the rest of the files from the build context into the container's working directory.
For example:
Your frontend project          Container
─────────────────────          ─────────
src/                         → /usr/src/app/src/
public/                      → /usr/src/app/public/
index.html                   → /usr/src/app/index.html
vite.config.js               → /usr/src/app/vite.config.js


This copies files into the image during the build. It does not automatically keep your local files synchronized with the container. Later, we'll discuss how Compose volumes enable live development.


Line 6 — Start the development server
CMD ["npm", "run", "dev", "--", "--host", "0.0.0.0"]


This tells the container what command to run by default when it starts.
- npm run dev runs the development script from package.json.
- -- tells npm to pass the following arguments to the script.
- --host 0.0.0.0 allows Vite to listen on the container's network interfaces, rather than only its internal loopback address.
Why does this matter? A server listening only on localhost inside the container may not be reachable from outside it. Binding to 0.0.0.0 makes it possible for Docker networking and port mapping to expose the development server.
One more important distinction: the Dockerfile does not itself publish a port. We will configure the port mapping later in docker-compose.dev.yml.

Step 1.3 — Choose the right installation command
Your package.json lists the dependencies, but I haven't yet confirmed whether your project has a package-lock.json.
There are two possible commands:
- npm install — installs dependencies and can update the lockfile.
- npm ci — installs dependencies from an existing lockfile, requires it to match package.json, and is generally better suited to repeatable builds.
Let's check before choosing.
Run this in your current PowerShell terminal:

Get-ChildItem package.json, package-lock.json



If package-lock.json exists, we'll use npm ci. If it doesn't, we'll use npm install for now.

Step 1.4 — Create dev.Dockerfile
First, understand npm ci
Your two files have different responsibilities:

package.json
Describes the dependencies your application needs, such as React, Vite, and Apollo Client.




package-lock.json
Records the resolved dependency versions so installations can be reproduced consistently.




npm ci
Installs dependencies using the lockfile. It fails if the lockfile and package.json are inconsistent, rather than silently updating the lockfile.


Follow the build process

Think of it like following a recipe: package.json describes what you need, while package-lock.json records the specific versions to use.
